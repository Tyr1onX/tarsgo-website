# 全站性能审计与首轮优化记录

## 测量范围与方法

- 基线代码：`main`，PR #85 合并后的提交 `2ef431c`。
- 生产基线：2026-10-16 使用 Lighthouse 13.5.0、Chrome 无头新模式，对 `https://jijiamaster.com` 冷缓存测量；公开页使用移动端预设，首页另测桌面端。
- 本地对照：同一台机器、同一个 Vite 预览地址，分别用基线构建和本分支构建测量；移动端使用 Lighthouse 移动预设，桌面端使用桌面预设。
- 总传输量和请求数取自 Lighthouse Network Requests；视频播放会发起未完成的 HTTP 206 分段请求，因此一轮 Lighthouse 结束时的媒体字节数不等于整段文件大小。分段请求长度会随运行时刻变化，不能据此推断整段视频的流量节省。
- 真实页面检查和截图均在隐藏 Chrome / 无头 Chrome 中完成，不会显示浏览器窗口或改变用户前台窗口。截图在本目录 `screenshots/`。
- `/dashboard` 基线未登录，只能测到访客状态；没有可用的隔离测试账号，因此登录后的工作台请求链路尚未实测。

## 瓶颈排序

1. **首页宣传视频**：`hero-showreel.mp4` 为 17,184,321 bytes（约 17.18 MB），1280×720、约 30 fps、114.73 秒。它在播放期间发起大量媒体分段传输，并且 HEVC 的浏览器支持不如 H.264 普遍。
2. **首页真实照片**：首页图片资源在生产移动端传输了约 1.38 MiB；Lighthouse 的图片尺寸/格式审计估算可节省约 1,077 KiB。六张专题照片中有多张是 1920px 以上的大图，适合在保持原图和构图的前提下补充响应式派生图。
3. **固定 URL 的静态资源缓存**：生产 `hero-robot.webp` 响应带 `Cache-Control: public, max-age=31536000, immutable`，同时 URL 没有内容哈希，Cloudflare 返回 `HIT`。这会使固定 URL 内容更新后仍可能被浏览器/CDN沿用一年，是明确的缓存正确性风险。
4. **外部字体**：Google Fonts CSS 是一条外部样式请求，生产首页字体约 96.8 KB；Inter 字体请求约 73.6 KB，Geist Mono 约 23.2 KB。应先确认页面字形实际使用和许可证，再评估自托管能否改善首屏。
5. **JS/CSS**：本地生产构建中首页专属 JS 为 97.04 KB raw / 27.04 KiB gzip；共享客户端入口为 183.13 KB / 58.04 KiB gzip，JSX runtime 为 129.03 KB / 42.51 KiB gzip；根 CSS 为 191.91 KB / 31.56 KiB gzip。已有路由分块，招新管理最大独立 chunk 为 67.95 KB / 16.76 KiB gzip。首页 JS 有进一步拆分空间，但当前传输量远小于视频和图片，优先级低于媒体与图片。

## PR 1：首页宣传视频资源

- 用 H.264 重新编码同一段宣传视频，保留 1280×720、约 30 fps、114.73 秒及原有 AAC 音轨；新文件采用内容哈希文件名，以匹配当前静态资源长期缓存策略。
- 新文件为 11,539,312 bytes（约 11.54 MB），比原始文件少 5,645,009 bytes，完整文件体积降低 32.85%。SSIM 全帧平均值为 0.984470；抽帧对照确认机器人主体、镜头和画面构图保留。
- Chrome 移动网络仿真下，旧编码约在 5.16 秒出现可绘制视频帧，新编码约在 5.60 秒出现；这是单轮无头浏览器观察，候选编码首帧约晚 0.44 秒。Lighthouse 移动端页面 LCP 的本地多轮结果为基线 4.29–4.30 秒、候选 3.85–4.29 秒；FCP 均约 2.50 秒、CLS 为 0。结果范围重叠，**不宣称首屏 LCP 有确定改善**。
- Lighthouse 网络结束时视频仍是未完成的 206 分段请求；本地移动端总传输量的单轮配对值为 5,221,745 → 5,221,756 bytes，另一轮为 4,894,065 → 4,828,540 bytes。请求数均为 47。由于媒体分段长度与播放进度变化，这些快照不能证明首屏即省下完整文件差额；可确定的收益是视频完整下载时少传 5.65 MB。
- 桌面端本地单轮值：LCP 1.47 → 1.42 秒，FCP 0.90 → 0.63 秒，CLS 均约 0.001，总传输量 4,894,065 → 4,828,540 bytes，请求数均为 47。单次样本仅作记录，不作为稳定收益结论。

## PR 2：首页专题照片响应式资源

- 基于 PR #87 合并后的 `main`，于 2026-10-17 在同一台机器、相同 Lighthouse 13.5.0 / Chrome 无头环境、本地 Vite 生产预览对照；before 为提交 `1dcbf38`，after 为本 PR 构建。每个场景各跑一轮，分数和 LCP 仅记录，不作为稳定改善结论。
- 为「认识吉甲」「赛事与荣誉」「低空微专业」三张大图新增内容哈希 WebP 的 640px 与 1280px 候选，并按卡片实际布局提供 `srcset` / `sizes`。浏览器实测：移动配置选择 1280px 候选，桌面配置选择 640px 候选。保留原始三张照片及原 URL 作为回退；同时复用作视频 poster 的机器人照片不另发响应式副本，避免同一屏重复下载。
- 三张原图为 698,364 bytes；桌面实际选择的 640px 资源为 149,832 bytes，移动配置选择的 1280px 资源为 370,896 bytes。浏览器 Network 统计的整页图片传输更能反映其他图片与协议开销：移动端 1,446,478 → 1,118,200 bytes，减少 328,278 bytes（22.7%）；桌面端 1,446,478 → 897,136 bytes，减少 549,342 bytes（38.0%）。请求数保持不变，分别为 48 / 47。
- Lighthouse 单轮结果：移动端 LCP 8.11 → 7.21 s、FCP 3.36 → 3.55 s、CLS 均为 0、整页总传输 4,828,666 → 4,500,672 bytes；桌面端 LCP 0.90 → 1.20 s、FCP 均为 0.62 s、CLS 均为 0、总传输 5,549,435 → 4,148,409 bytes。媒体分段在桌面两次运行间少了 851,968 bytes，说明整页总量受视频播放进度影响；移动端总量变化主要对应图片变化。移动 LCP 与桌面 LCP 方向相反，均为单次测量，因此不宣称 LCP 获得稳定改善。
- 隐藏无头 Chrome 以 1440×960、412×900 视口检查首页专题照片及黑金 / 白金主题；原有六张照片顺序、裁切和卡片布局保留。四张真实浏览器截图见本目录 `screenshots/home-images-*.jpg`。
- 浏览器回归检查六个图片链接均可见、图片自然尺寸成功解码、键盘 Tab 可进入链接、页面无横向溢出，黑金 / 白金主题均正确，移动 DPR 2 选择 1280px 候选、桌面 DPR 1 选择 640px 候选。由于本地 Vite 预览未运行认证后端，既有 `/api/me` 探测返回 502；此次只影响预览中的登录状态展示，与图片资源无关。未观察到图片加载错误。

## 后续建议

1. 单独修正静态缓存策略：只有带内容哈希的构建资源使用一年 `immutable`；固定 URL 的照片和媒体应可重新验证，并用后端测试确认缓存头与条件请求行为，再检查 Cloudflare 实际响应。
2. 检查 Google Fonts 中实际使用的字族、字重和字体许可证，再决定是否自托管；不能仅因外部请求而盲目增加仓库字体。
3. 评估把首页未使用的公开档案组件从 `home` chunk 拆出。拆分前后以实际主页脚本字节和页面切换耗时决定是否保留。
4. 为 `/dashboard`、`/dashboard/base` 和招新管理补充隔离账号下的认证后测量；当前未登录页面数据不能代替工作台真实请求链路。
